# Primary-led T3 workers

T3 mode keeps your current Codex or Claude model as the primary you talk to.
Instead of asking Jev to classify prompts in a proxy, the primary follows
instructions to route bounded subtasks to T3 workers. This is opt-in and
instruction-driven: it is not a request interceptor or a guarantee that every
primary model will follow the instructions.

## Set up global routing

Build this fork from its checkout first:

```sh
npm ci
npm run build
```

The upstream published npm package does not include these T3 commands. Run the
built checkout with its actual absolute path:

```sh
node /absolute/path/to/switchboard/bin/switchboard.mjs t3 init --global
```

Setup adds short managed pointers to `~/.codex/AGENTS.md` and
`~/.claude/CLAUDE.md`. If `~/.codex/AGENTS.override.md` already exists, it is
used instead of `AGENTS.md`. The installer respects `CODEX_HOME` and
`CLAUDE_CONFIG_DIR`; if your T3 providers use custom homes, those values must
match the homes configured in T3 when you run setup.

The pointers apply only to a primary session that has T3's
`orchestrator_capabilities` and `delegate_task` tools. They refer to the shared
workflow in `t3-instructions.md` under the Switchboard configuration directory.
Setup preserves unrelated instructions and an existing `t3-policy.json`, and
saves owner-only backups of original instruction files under
`t3-global-backups` in that directory. It creates a default policy if one is
absent. The directory is `$SWITCHBOARD_HOME` when set, otherwise the standard XDG
configuration path.

Start a new T3 conversation to pick up the instructions. Existing conversations
may retain their previous context. A project instruction or explicit user request
can disable Switchboard or select different worker settings for that task.

Inspect the saved setup or remove its pointers with:

```sh
node /absolute/path/to/switchboard/bin/switchboard.mjs t3 status --global
node /absolute/path/to/switchboard/bin/switchboard.mjs t3 uninstall --global
```

Status reports the saved files; it does not prove a live worker ran. Uninstall
removes only the managed pointers and preserves other instructions, policy,
workflow, and backups. It uses the same provider home environment variables as
setup.

## Set up one project

For project-only routing, run this command from the target project directory:

```sh
node /absolute/path/to/switchboard/bin/switchboard.mjs t3 init
```

This adds the full managed instruction block to that project's `AGENTS.md` and
creates `t3-policy.json` if absent. Existing policy overrides and unrelated
project instructions are preserved. `switchboard t3 instructions` prints the
project block; `switchboard t3 policy` prints the complete effective policy.

In the examples below, `switchboard` means that same built executable, or this
fork installed locally. The generated instructions pin the executable and policy
directory paths, so keep the checkout in place and rebuild after source changes.

## Routing flow

Delegate every substantive request, including research, analysis, coding, and
substantive answers. The primary scopes the work, assigns workers, verifies
results, and synthesizes the response. Simple acknowledgments and logistics stay
direct. Use one worker for a small task; split independent work across as many
workers as useful, with disjoint ownership and dependent stages sequenced.
Explicit user requests and project constraints still take precedence.

The primary obtains current worker/provider availability with `orchestrator_capabilities`, then calls `switchboard t3 route` with JSON on stdin. The request shape is:

```json
{"task":"Add a small validation helper and cover its edge cases","tier":"routine","family":"codex","capabilities":{"providers":[]}}
```

Use the actual capability snapshot in place of the empty providers array. `family` is `codex` or `claude`; tier is `routine`, `standard`, `complex`, or `demanding`. The command returns a tier, an exact provider/model/options selection, an async T3 delegation description, and `verificationRequired: true`. The primary forwards the delegation to `delegate_task`, follows its async `next`, and verifies the result before integrating it. It does not poll.

The primary chooses the task tier and provider family for each task, while keeping its own model. It may use Codex and Claude workers in the same conversation. For example, 10 Luna workers for independent routine tasks versus 2 Sonnet workers for a different work structure illustrates a choice, not measured efficiency or a fixed rule. Context duplication, coordination, and retries affect the tradeoffs; savings and result quality are not guaranteed.

Escalation requires a reported failure, a strictly stronger tier, and a different model. Instructions allow at most two escalations; at the limit, the primary reports the blocker. The router checks exact catalog availability and supported effort; unavailable selections fail instead of silently substituting another model. Escalation limits are instruction-driven, not globally persisted or enforced.

Global instructions tell worker or child sessions to complete their assigned
task without delegating again. Switchboard also marks its worker assignments with
`SWITCHBOARD_WORKER`. These are instruction-based safeguards, not runtime
enforcement; a model can fail to follow them.

T3 mode makes no classifier or provider call itself. The JSON task is used to form the returned worker task; Switchboard does not store it or call a model. T3 and native harnesses may retain their own transcripts. Native authentication, approvals, sandboxing, and tool behavior remain owned by the harness. Cost, quality, and provider coverage have not been benchmarked; automated tests use synthetic providers, and live tests require explicit authorization.

## Defaults

The default Codex tiers are Luna, Terra, Sol, and Astra. Claude tiers are Haiku, Sonnet, Opus, and Fable. Exact model IDs and effort settings live in the effective T3 policy; provider capability is checked at route time. Edit `t3-policy.json` to match the models available to your account.

The policy is a complete document, separate from the legacy `policy.json`.
`switchboard t3 policy` prints a valid starting point. Each family has all four
tiers; each tier has an exact `model` ID and an optional `effort`:

```json
{"model":"gpt-6.1-terra","effort":"medium"}
```

There is no fuzzy model matching or automatic model-version upgrade. Choose a
currently advertised ID and supported effort. Remove `effort` to return empty
options and use native defaults. Rerouting after a failed routine worker uses
`"tier":"standard"` plus
`"previous":{"tier":"routine","model":"gpt-6-luna","failure":"Describe the failed acceptance check"}`.
The new task must carry forward the useful findings. The planner checks the
reported escalation; it does not independently run checks or persist attempt counts.

The legacy `switchboard claude` and `switchboard codex` proxy routing remains available separately; see [legacy routing](routing.md).
